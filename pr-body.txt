#### Refactor 2 — Dashboard `now` memo-stability bug

The dashboard's `cronCaptions` and `sessionWindowSubtitle` `useMemo`s both depend on `now`, but `now` was declared as `const now = new Date().getTime()` directly in the render body — a brand-new number on every render. **This made the `useMemo` dependency array change on every render, defeating the entire purpose of the memo.** Two 3-line `for` loops ran on every keystroke, on every parent re-render, and on every sub-component re-render.

**The fix:**
```ts
// Before:
const now = new Date().getTime();

// After:
const [now, setNow] = useState(() => new Date().getTime());
useInterval(() => setNow(new Date().getTime()), { ms: 30_000 });
```

`useState` initializer runs once on mount, so `now` is stable for 30s windows. The 30s `useInterval` refreshes it (close to the monitor's 10s poll cadence — 30s gives the caption rounding a stable window so "Running in 30s" doesn't flicker to "Running in 29.95s" 50ms later).

**Why this is byte-equivalent:**
- `computeCronJobRowCaption(job, now)` rounds to the nearest scheduling boundary (e.g. "Running in 30s", "Active — next at 14:35"). The string output is identical for `now` ± a few hundred ms.
- `countInWindow(sessions, windowMs, now)` compares against a window boundary (5 min for "active", 7 days for "last 7d"). The boolean is identical for `now` ± a few seconds.

**The caption and subtitle render the same string they did before — they just no longer recompute on every render.** The dashboard's `setData` updates (poll responses, cron schedule changes, etc.) still invalidate the memos because the `monitor` and `monitor?.cron.jobs` deps change. The new behavior is strictly more efficient, and the rendered output is byte-equivalent.

### What changed (this session — session 88)

#### Refactor 1 — `JobFormModal.tsx` populate-block collapse (14 lines → 8 lines)

The `useEffect` that populates the form on modal open had two near-identical 7-line branches — one for "edit mode" (read from `job`) and one for "create mode" (reset to defaults). The refactor collapses the two branches into a single block by introducing a `source = job?.id ? job : null` binding and using `source?.field ?? default` (or `|| default` for falsy-only fallbacks). The 7 fields covered are: `name`, `schedule`, `prompt`, `deliver`, `model`, `profile_name`, `repeat`.

**Why this works (byte-equivalence argument):**
- `setName(job.name ?? "")` ≡ `setName(source?.name ?? "")` for both null source (reset) and non-null source (edit). When `source = null`, `source?.name` is `undefined`, so `?? ""` fires and returns `""`. When `source = job`, `source.name` is `string` and `?? ""` only fires on null/undefined, not on empty string.
- `setDeliver(job.deliver || "none")` ≡ `setDeliver(source?.deliver || "none")` for the same reason — `||` fires on any falsy value, so null source and `deliver = ""` both produce `"none"`.

…and **3 of the 5** sites then folded with `tags.length > 0 ? tags : undefined` so the JSON body omits the `tags` key when blank (matches the Hindsight API contract — `tags: []` is silently treated as "no tags", but `tags: undefined` is what the rest of the Hindsight code path produces and keeps the wire payload tight).

### Refactor 2 — `setField(setter, key)` helper for 12× inline modal setter bodies

The 4 Hindsight modals each take 3-4 separate `onNameChange` / `onContentChange` / `onPriorityChange` / `onTagsChange` / `onQueryChange` props. The original JSX inlined the same `(v) => setForm(p => ({ ...p, key: v }))` setter body **12 times** (4 props × 3 modal bodies, minus the 0-prop AddMemoryModal):

```tsx
onNameChange={(v) => setDirForm(p => ({ ...p, name: v }))}
onContentChange={(v) => setDirForm(p => ({ ...p, content: v }))}
onPriorityChange={(v) => setDirForm(p => ({ ...p, priority: v }))}
onTagsChange={(v) => setDirForm(p => ({ ...p, tags: v }))}
```

Extracted to a small file-local generic helper:

```ts
const setField = <S,>(
  setter: React.Dispatch<React.SetStateAction<S>>,
  key: keyof S,
) => (v: S[keyof S]) => setter((p) => ({ ...p, [key]: v }));
```

Call site collapses to:
```tsx
onNameChange={setField(setDirForm, "name")}
onContentChange={setField(setDirForm, "content")}
...
```

**Why I rejected `useCallback` wrapping the helper itself:** the helper returns a NEW closure per call, so `useCallback([], ...)` on the outer factory doesn't stabilise the per-key closures. Wrapping the *inner* closure with `useCallback(..., [setter, key])` would require hoisting the per-key call out of the JSX (one `useMemo` per call), which costs more than it saves. The current shape is the right trade-off.

**Byte-equivalence audit:** the helper invokes the `setter` callback with the exact same `(p) => ({ ...p, [key]: v })` shallow-update closure. React's state-update batching treats the inline arrow and the helper-returned arrow identically.

### Refactor 3 — Type the dashboard polling `extract` array, remove the `any` cast

The dashboard polls 3 endpoints on independent intervals via a declarative `polls: [{url, ms, extract}]` array. The `extract` field was typed inline as `(d: { data?: unknown }) => ...`, and the `pollIntervals.map()` consumer had to cast it via `(extract as (d: any) => any)` to drop the per-element type into the async loop. The result was a single `eslint-disable-next-line @typescript-eslint/no-explicit-any` comment on the cast.

Replaced with a module-local `PollExtractor` alias:

```ts
type DashboardUpdate = Partial<Pick<typeof data, "monitor" | "processes" | "missions">>;
type PollExtractor = (d: { data?: unknown }) => DashboardUpdate | null;
const polls: Array<{ url: string; ms: number; extract: PollExtractor }> = [...];
```

The consumer now calls `extract(raw)` directly with the type checker verifying the return shape. The `eslint-disable` is gone. The 3 inline `(d: { data?: unknown }) =>` parameter types on the extractor functions collapse to the inferred `(d) =>`.

Pre-refactor, `useCronJobs` and `useSystemCronJobs` each had their own (id: string) => Promise<void> handlers for toggle / delete / pauseAll. ```ts
const { handleToggle, handleDelete, handlePauseAll, pauseAllBusy } =
  useCronJobMutation<CronJob>({
    endpoint: "/api/cron",

### Refactor 3 — `cron/page.tsx` onEdit type narrowing (4-line runtime check → discriminated handler)

**File:** `src/app/orchestration/cron/page.tsx`

The page had two near-identical 4-line inline runtime checks that discriminated the onEdit callback by kind:

```tsx
onEdit={(job) => {
  // Wide type because TabButton can dispatch either kind; on
  // the agent tab runtime the value is always CronJob, so any
  // `command` field means we're seeing the wrong type.
  if ("command" in job) return;
  setEditingJob(job);
  setShowCreate(true);
}}
```

The `if ("command" in job) return;` is a runtime type guard that should be a TypeScript-level concern. The cleaner shape is to thread the onEdit handler directly through the `JobCard`/`SystemCronCard` with a `CronJob`-or-`SystemCronJob` union type, and let the call site cast at the use boundary (where it knows which kind it has):

```tsx
// Before
onEdit={(job) => {
  if ("command" in job) return;
  setEditingJob(job);
  setShowCreate(true);
}}

// After
onEdit={(job) => {
  setEditingJob(job as CronJob);
  setShowCreate(true);
}}
```

The runtime check is gone; the `as CronJob` / `as SystemCronJob` cast lives at the only boundary that has the type knowledge (the parent's per-tab render branch). The `CronTabContent` no longer needs to perform runtime discrimination — the parent's `isAgent` discriminator flows through, and the per-card components accept the appropriate subtype.

**Files changed:** `src/app/orchestration/cron/page.tsx` (4-line check + 4-line mirror + their comments collapsed to 2 1-line casts, ~25 lines net reduction).

JSDoc updated with the new contract: "The `successMsg` can be a static string (the common case) or a function returning a string. The function form is for handlers where the success message depends on a mode/state that the caller has already computed."

(1) **`runDeployAction` helper in `src/components/layout/Sidebar.tsx`** — collapsed three near-identical 30-line click handlers (`handleUpdate`, `handleRestart`, `doRebuild`) into one parameterized `useCallback` plus three 5-line wrappers. The 3 handlers shared the same fetch + error-parse + pollDeployStatus + catch shape; the only differences were the action name, the started/running messages, the busy setter, the body, and whether to read the success body for `d.error`. (2) **`fallbackForDeployMessage()` helper in `src/lib/deploy-action-fallback.ts`** — extracted the `startedMessage.replace(/started.*$/, "failed")` regex into a named, unit-testable function. 7 unit tests cover the 3 message shapes the Sidebar actually uses plus 4 edge cases (empty, no-match, multi-match, capitalization). The "Restart requested" message does NOT include "started", so the regex returns the input unchanged — a pre-existing quirk locked in by the test so a future "fix" of the restart message is intentional.

Bonus: 4 inline `err instanceof Error ? err.message : <fallback>` patterns in `Sidebar.tsx` (consolidated into 1 in `runDeployAction`) + 1 in `src/app/(main)/sessions/[id]/page.tsx` migrated to the new `messageFromError()` helper from session 77. After session 78, the `err instanceof Error` pattern in `src/components/` is reduced from 4 to 0 sites.

All 1197 tests pass (189 suites, +7 from this session). tsc clean, eslint clean, build passes. Byte-equivalent at runtime (same fetch URL, same body, same poll behavior, same error envelope) for the 3 deploy actions. 1 documented quirk preserved: the restart catch block sets the message to the literal startedMessage on network failure (no "started" word to match). Pre-existing behaviour.

### What was rejected this session

- **`useApiData` adoption in `(main)/logs/page.tsx`** — out of scope for "AT LEAST identical results". The hook doesn't support the auto-refresh + abort pattern the logs page uses. A full sweep is a behaviour change (removes the `setRefreshing` micro-state, changes the abort timing).
- **`HindsightBrowser` 4-site `runMutation` migration** — the 4 sites are toggle/delete handlers that don't have a single `isValid` + `busy` + `build` shape. Forcing the migration would change the success toast semantics.
- **`Sidebar.tsx` 3-handler consolidation into a single `handleAction(action: DeployAction)`** — would force the click handlers to pass the action name from the JSX (`onClick={() => handleAction("update")}` vs `onClick={handleUpdate}`). The wrapper-per-action pattern is more discoverable in the JSX and matches the existing pattern from the rest of the codebase (e.g. MissionCreateForm, JobFormModal).
- **`fallbackForDeployMessage` "fix" for the restart no-match quirk** — the restart message ("Restart requested…") doesn't match the "started" regex, so the helper returns it unchanged. Fixing would require a different regex or a per-action fallback string — out of scope for "AT LEAST identical results" and would change the user-visible string on a network failure.
