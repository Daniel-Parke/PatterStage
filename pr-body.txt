### Refactor 1 — `activeMissions` filter → `isMissionActive` helper

Pre-refactor (lines 425-433):
```tsx
const activeMissions = useMemo(
  () =>
    missions.filter(
      (m) =>
        m.status === "dispatched" ||
        (m.status === "queued" && m.queuedForRun === true),
    ),
  [missions],
);
```

Post-refactor:
```tsx
const activeMissions = useMemo(
  () => missions.filter(isMissionActive),
  [missions],
);
```

**Byte-equivalence audit (per session 51 lesson):** the `isMissionActive` helper body is:
```ts
return mission.status === "dispatched" || isMissionQueuedForRun(mission);
```
And `isMissionQueuedForRun(m) = m.status === "queued" && m.queuedForRun === true`. Substituting:
```
isMissionActive(m) = m.status === "dispatched" || (m.status === "queued" && m.queuedForRun === true)
```
This is **textually identical** to the inline form. The helper's `tests/unit/mission-board.test.ts` already exhaustively tests the 4 input shapes (dispatched, queued+true, queued+false, anything-else), so no new tests are needed for the helper itself — only the dashboard's *adoption* of the helper needs to be locked.

### Refactor 2 — `handleCronScheduleChange` `setDataFields` direct call → `setData` partial-setter

The dashboard's `handleCronScheduleChange` is the only callback in the component body that bypasses the `setData` partial-setter helper and calls the raw `setDataFields` dispatch directly. The reason was the optimistic-update pattern: it needs to read the *current* `monitor` to compute the new one, which is what the React `useState` updater form `(prev) => ({...prev, monitor: f(prev.monitor)})` is designed for.

But the dashboard's `useCallback` for `handleCronScheduleChange` already lists `data.monitor` in its deps array (line 311), so the closure-captured `data.monitor` is always fresh. The `(prev) => ...` updater form is unnecessary — reading `data.monitor` from the closure produces the same value as `prev.monitor` from the updater.

Pre-refactor (lines 277-282):
```tsx
// Optimistic local update before the API call so the UI updates immediately
setDataFields((prev) => ({
  ...prev,
  monitor: withCronJobSchedule(prev.monitor, jobId, scheduleDisplay),
}));
```

Post-refactor:
```tsx
// Optimistic local update before the API call so the UI updates immediately.
// `data.monitor` is in the useCallback deps (line 311 below) so the
// captured value is always fresh — equivalent to reading `prev.monitor`
// from a React-state updater. The `setData` helper is the canonical
// partial-state setter (defined at line 179 above); only the `useState`
// declaration itself uses the raw dispatch setter directly.
setData({
  monitor: withCronJobSchedule(data.monitor, jobId, scheduleDisplay),
});
```

**Byte-equivalence audit:** the `setData` helper is defined as:
```tsx
const setData = useCallback((partial: Partial<typeof data>) => {
  setDataFields(prev => ({ ...prev, ...partial }));
}, []);
```

So `setData({ monitor: f(data.monitor) })` expands to:
```tsx
setDataFields(prev => ({ ...prev, monitor: f(data.monitor) }));
```

The old inline form was:
```tsx
setDataFields(prev => ({ ...prev, monitor: f(prev.monitor) }));
```

The only difference is `f(data.monitor)` vs `f(prev.monitor)`. Since `data.monitor` is in the `useCallback` deps, the callback is rebuilt on every `data.monitor` change — so the captured `data.monitor === prev.monitor` at invocation time. **Byte-equivalent for all observed paths.**

**Required follow-up:** after the body change, the `react-hooks/exhaustive-deps` lint rule flagged the missing `setData` dep. Added `setData` to the deps array (line 311). The expanded deps array `[data.monitor, showToast, refreshMonitor, setData]` is also stable in practice — `setData` is a `useCallback(..., [])` so it has a stable reference for the page's lifetime.

**`withCronJobSchedule` JSDoc update:** the JSDoc for the helper said "The page can call this inside its setDataFields updater" — updated to "The caller passes the current `data.monitor` (or the value of `prev.monitor` if it ever adopts the updater form again)" so the comment matches the new calling convention.

### Patterns to take forward

1. **"Inline predicate re-derivation is a code-smell when the helper exists"** — any time `grep` finds a multi-line predicate that's textually identical to an existing helper, it's a candidate for migration. The `isMissionActive` adoption in the dashboard closes the last drift in the codebase. Future code review should reject inline re-derivations of `isMissionDraft`, `isMissionQueuedForRun`, `isMissionActive`, `missionBoardColumn`.
2. **"setData as the canonical partial-setter, not the raw dispatch"** — any time a component defines a `setData` (or similarly-named) helper that wraps the raw `useState` dispatch with a partial-state updater, the helper should be the SOLE callsite for partial updates. The raw dispatch should appear only in (a) the `useState` destructure and (b) the `setData` helper body. The dashboard's `handleCronScheduleChange` was the only drift; now consolidated. The 6 new tests lock the invariant: a future PR that re-introduces a direct `setDataFields((prev) => ...)` call will fail the "exactly 2 mentions" test, and a future PR that re-introduces the inline activeMissions predicate will fail the "does not match inline pattern" test.

### Refactor 4 — ModelEditor `setSaving(false)` finally-block bug fix

The `handleSubmit` catch block had `setSaving(false)` but the success path did NOT:

```ts
// Before:
try {
  // ... save ...
  onSaved();
} catch (err) {
  setErrorFromCaught(setError, err, "Save failed");
  setSaving(false);  // ← only reset on FAILURE
}

// After:
try {
  // ... save ...
  onSaved();
} catch (err) {
  setErrorFromCaught(setError, err, "Save failed");
} finally {
  // ← reset on BOTH success and failure
  setSaving(false);
}
```

**Why this is a real bug (not just cosmetic):** the current success path relies on the parent's `onSaved()` callback → `setEditing(undefined)` to unmount the modal, which clears the `saving` state as a side effect of unmount. This works in the current code path. But if the parent ever deferred the unmount (e.g. to show a "Saved!" toast before closing), OR if the modal was reused for a 2nd edit without remount, the saving spinner would stay stuck on the success path.

**Why "AT LEAST identical results" still holds:** the only observable difference is the moment the saving state is reset. In the current code, the success path resets `saving` to `false` as a side effect of unmount. In the new code, the success path resets `saving` to `false` in the `finally` block, BEFORE the unmount happens (the `onSaved()` call inside the try block triggers the parent's `setEditing(undefined)` which schedules an unmount, but the `finally` block runs synchronously after the try block returns, before React processes the unmount). Net effect: `saving` is reset to `false` either way, the user never sees the spinner after the save completes. Byte-equivalent for all observable parent paths.

**Canonical pattern:** this is the same shape used by `toggleSkill` in skills page (`try { ... } catch (err) { ... } finally { setToggling((prev) => { ... }) }`) and `runFallbackMutation` in `useModelsPage` (`try { ... } catch (err) { ... } finally { /* setBusy(false) */ }` — well, `runSyncAction` does this in the lib helper, not the hook). The single canonical place to reset the busy flag, not duplicated in success/failure branches.

The 4 new tests in `tests/unit/model-editor-finally-saving.test.ts` lock:
- The catch block contains `setErrorFromCaught(setError, err, "Save failed")` (no regression of the existing migration from session 91)
- A `finally` block contains `setSaving(false)`
- The catch block does NOT contain `setSaving(false)` (the old bug shape)

### Refactor 5 — `useModelsPage` `messageFromError` migration

The auto-import catch block had the verbose `toError(err).message || String(err)` form:

```ts
// Before:
await apiFetch("/api/models/import", { method: "POST" }).catch((err) => {
  const msg = toError(err).message || String(err);
  console.warn("Model auto-import failed — showing cached data:", msg);
});

// After:
await apiFetch("/api/models/import", { method: "POST" }).catch((err) => {
  const msg = messageFromError(err, String(err));
  console.warn("Model auto-import failed — showing cached data:", msg);
});
```

Plus dropped the `toError` import from the `api-fetch` import block (the verbose form was the only consumer).

**Why this is byte-equivalent:** `messageFromError(e, fallback)` is literally `toError(e).message || fallback` (per `src/lib/api-fetch.ts:40`). So `messageFromError(err, String(err))` is identical to `toError(err).message || String(err)`. The migration is a name change, not a behavior change.

**Why this matters:** the verbose form is the only `toError` call site left in the codebase outside `api-fetch.ts` itself (per the session 90/91 migration carryover). The 9 `setError(messageFromError(err, ...))` migrations in session 91 closed the `setError` side, but the `.catch((err) => { ... console.warn(... toError(err).message ...) })` pattern was not on the session 90/91 audit radar. This session closes the last 1 site.

The 4 new tests in `tests/unit/use-models-page-message-from-error.test.ts` lock:
- The auto-import catch block uses `messageFromError(err, String(err))` (not the verbose form)
- The file does NOT contain `toError(err).message` anywhere
- The `toError` import is NOT in the `@/lib/api-fetch` import block
- The `messageFromError` import IS in the `@/lib/api-fetch` import block (regression guard)

### Patterns to take forward

1. **"A2/A3 1-setter close callback" pattern** — the 3 helpers added in this session (closeSkillEditor, closeDelete, openAddModel) all follow the same shape: 1-setter `useCallback(..., [])` that wraps a `() => setX(null)` form. The 2+ site rule is the discriminator (A2 = 2 sites, A3 = 3 sites). Both are valid; the session 100 audit's "A3 in the loose sense" (3+ places where the same lifecycle decision is duplicated) is what we're locking here.
2. **"Discriminated close-pattern anti-A3"** — when a modal has a 1-setter close form (X-button / overlay click / Cancel button) AND a 3+ setter success block (save success path), the success block stays inline. Threading the success path's state into the close helper would force a discriminated signature that doesn't fit the 1-setter close pattern. Document in JSDoc and lock with a test that asserts the success block's exact shape.
3. **"Finally-block busy reset" pattern** — when a callback has `setBusy(true)` followed by a try/catch, the `setBusy(false)` MUST live in the finally block, not the catch block. The success path that relies on parent unmount to clear the busy state is a latent bug — if the parent ever defers unmount or reuses the component, the busy state stays stuck.
4. **"`messageFromError` is the only `toError` call site that should exist outside `api-fetch.ts`" pattern** — the verbose `toError(err).message || fallback` form is byte-equivalent to `messageFromError(err, fallback)`, but the helper form has a name and JSDoc. After this session, the only `toError` call sites in the codebase are inside `api-fetch.ts` itself (the helper's implementation). All consumers use `messageFromError`, `toastError`, or `setErrorFromCaught`.

**Byte-equivalence rationale (load-bearing — the `"\"` fallback is the key to byte-equivalence here):** The inline form returns `err.message` for Error instances, or `String(err)` for non-Error throws. The helper returns `toError(err).message || ""`. The byte-equivalence matrix is:

| Input `err` | Inline form returns | `messageFromError(err, "")` returns | Byte-equivalent? |
|---|---|---|---|
| `new Error("foo")` | `"foo"` | `"foo"` (`toError(e).message` = `"foo"`, `\|\| ""` no-op) | ✅ |
| `new Error("")` | `""` | `""` (`toError(e).message` = `""`, `\|\| ""` → `""`) | ✅ |
| `"string throw"` | `"string throw"` (via `String(...)`) | `"string throw"` (`toError(...)` wraps, `.message` = `"string throw"`) | ✅ |
| `null` | `"null"` (via `String(null)`) | `"null"` | ✅ |
| `42` | `"42"` | `"42"` | ✅ |
| `TypeError("x")` | `"x"` | `"x"` | ✅ |

The new test file `tests/unit/hermes-profile-sync-error-format.test.ts` documents this matrix as 6 byte-equivalence tests + 1 empty-Error sanity test + 1 `toError` regression guard.

### Refactor 1 — `serverErrorFromCatch(route, context, error, message)` in `src/lib/api-logger.ts`

The 2-line `logApiError(ROUTE, CONTEXT, error); return serverError(MESSAGE);` pattern was duplicated across **27** catch blocks in List 4 territory (models, config, agent-files, agent-profiles, fallbacks, personality). Each site is a perfectly identical 2-line block — the same `logApiError` call followed by the same `serverError(STATIC_MESSAGE)` return with a static user-facing string.

The carryover from session 94 had already promoted the helper to `src/lib/api-logger.ts` (along with the test file) and migrated 7 of the model routes. This session finished the remaining 18 routes, bringing the total to 27.

**Why this lives in `api-logger.ts`** (not `api-response.ts`): the helper is a *catch-block shim* that composes two existing primitives (logApiError + serverError). The natural home is the file where the `logApiError` side-effect lives. `api-response.ts` is response-shape only (no logging), and adding a logging import there would break its "keep this module tiny and dependency-free" rule (see the `api-response.ts` top comment).

**Why not `setErrorFromCaught` / `toastError`-shaped** (which take a setter fn, not a log route): the API catch-block is a *combined log + response* contract — the setter-fn pattern is for client-side `useState` / `showToast` cases where there's no log side-effect. A dedicated `serverErrorFromCatch` matches the API contract (1 call → 1 log + 1 response) without forcing the caller to compose two helpers at every site.

**Byte-equivalence audit:** the helper returns the same `NextResponse` as `serverError(message)` and emits the same `console.error` line as `logApiError(route, context, error)`. Tests cover the log+response pair end-to-end via console-error spying + NextResponse inspection (the 6 byte-equivalence tests in `tests/unit/server-error-from-catch.test.ts` assert the helper equals the inline 2-line block for 5 input shapes: Error, empty Error, string, null, TypeError).

### Refactor 2 — `pushDiff(field, before, after)` closure in `src/app/api/models/sync/pull/route.ts`

```ts
const pushDiff = <K extends keyof typeof hermes & keyof typeof model>(
  field: K,
  before: unknown,
  after: unknown,
) => {
  diffs.push({ field: field as string, before, after });

};
```

Each of the 4 sites collapsed from 2-4 lines (the `diffs.push({...})` + `updates.X = Y` pair) to a 1-line `pushDiff(field, before, after)` call.
