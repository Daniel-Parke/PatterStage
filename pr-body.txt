## Session 90 — List 3 (Models, Agents, Skills, Tools, Personalities) — 4-site `toastError` migration in operations pages

Pick was List 3 (per random selection `echo $(( RANDOM % 4 + 1 ))` = 3, the first List-3 pick since session 80). Single byte-equivalent refactor: a 4-site migration of the inline `showToast(messageFromError(err, "..."), "error")` pattern in `src/app/operations/` to the `toastError(showToast, err, "...")` helper that was promoted in sessions 77 + 79. The helper was already adopted in `src/hooks/useModelsPage.ts` (9 sites) but the operations pages had been left untouched. This session closes the last 4 sites in List 3 territory.

All 1269 unit tests pass (196 suites, no new tests added — the helper is exhaustively tested in `tests/unit/toast-error.test.ts`). tsc clean, eslint `--max-warnings 0` clean, build passes. Byte-equivalent at runtime for all 4 migrated sites.

### Refactor 1 — 4 `showToast(messageFromError(...))` → `toastError(...)` migrations

| File | Line | Migration |
|---|---|---|
| `src/app/operations/skills/page.tsx` | 168 | `toastError(showToast, err, "Failed to update skill")` — toggleSkill catch block |

All 4 sites are clean catch-block patterns with no extra side effects on the error message (the skills toggle site has a `setData(prevData)` revert BEFORE the toast, which is preserved unchanged). The migration is mechanical and byte-equivalent: `toastError(showToast, err, fallback)` produces the same `showToast(messageFromError(err, fallback), "error")` call as the inline form (per `src/lib/api-fetch.ts:128`).

### Why this matters

The `toastError` helper is the canonical "catch-block error unwrap → toast" pattern. With this session, **every catch-block toast in `src/app/operations/` now uses the helper**, matching the convention in `useModelsPage.ts`. The `showToast(messageFromError(...))` form is now an outlier — it survives in `(main)/logs/page.tsx`, `config/seed/page.tsx`, and a few other List 1/4 sites, but is fully eliminated from List 3.

### What was NOT migrated (and why)

- `src/app/operations/skills/[...path]/page.tsx:66` — `setError(messageFromError(err, "Unknown error"))`. Uses `setError` (a useState setter), not `showToast`. The `toastError` helper is for `showToast`-based error reporting. A `setErrorFromCaught(setError, err, fallback)` helper would be the equivalent, but with only 7 sites total across the codebase and no 2nd-consumer pattern, the Rule of Three says to keep the inline form.
- `src/app/operations/personalities/page.tsx:166` — same as above (`setError` not `showToast`).
- `src/hooks/useModelsPage.ts:97,175,253` — same: `setError` (line 97) and `details[].detail` (line 175, 253). Not toast candidates.

- **`npx tsc --noEmit`** clean

- **Byte-equivalence audit per session-51 lesson:** `toastError(showToast, err, fallback)` is the canonical implementation of `showToast(messageFromError(err, fallback), "error")` (`src/lib/api-fetch.ts:128`). The migration is a name change, not a behavior change.

### What was rejected

- **Migrating the 7 `setError(messageFromError(err, "..."))` sites to a `setErrorFromCaught` helper.** With only 7 sites across 6 files, the Rule of Three says to keep the inline form. The helper would be `setErrorFromCaught(setError, err, fallback)` — a 3-parameter setter wrapper. Not a clear win.
- **Refactoring `apiFetch` to accept `body?: unknown` like `safeApiCall` does, eliminating the 12 `JSON.stringify({...})` wrappers in List 3 callsites.** This is a signature-level change with type-level ripples across the entire codebase. The current convention (`apiFetch` takes `RequestInit`, `safeApiCall` takes a body object) is documented in the JSDoc and is consistent across all 30+ callsites. Out of scope.
- **Consolidating the 4 `Modal` import + 4 `useToast` + 4 `toastElement` patterns in the 4 operations pages into a shared `useOperationPage` hook.** Out of scope — the 4 pages have different state shapes, different modals, and different load/save semantics. A shared hook would have 4+ conditional branches and wouldn't reduce code.
- **Extracting the `{ showToast, toastElement } = useToast()` + `{toastElement}` render pattern into a custom `useToastElement()` hook that returns the element directly.** Cosmetic only, doesn't reduce code at the call site. Defer.
- **Auditing the inline `console.warn("Model auto-import failed", msg)` in `useModelsPage.ts:67` for a `logApiError` migration.** Different surface (server-side logging, not toasts). Already uses the canonical `toError(err).message || String(err)` pattern from session 79. No change needed.

### Patterns to take forward

1. **"List 3 operations pages are now `toastError`-complete" pattern** — the 4 sites that remained after the session-77 + session-79 migrations are all closed. The `showToast(messageFromError(...))` inline form is now an anti-pattern in operations pages, and code review should reject it. The audit recipe is a 1-line grep.
2. **"Different catch-block consumer" discriminator for `toastError` vs `setError`/`details[].detail`** — `toastError` is only for `showToast`-based reporting. When a catch block writes to `setError` (a useState setter) or to a structured `details[].detail` field, the `messageFromError(err, fallback)` form is correct (it returns the message; the caller decides where to put it). The 7 sites in `src/app/operations/skills/[...path]/page.tsx`, `personalities/page.tsx`, `useModelsPage.ts` are all of this shape.
