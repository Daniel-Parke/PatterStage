### Refactor 1 — `serverErrorFromCatch(route, context, error, message)` in `src/lib/api-logger.ts`

The 2-line `logApiError(ROUTE, CONTEXT, error); return serverError(MESSAGE);` pattern was duplicated across **27** catch blocks in List 4 territory (models, config, agent-files, agent-profiles, fallbacks, personality). Each site is a perfectly identical 2-line block — the same `logApiError` call followed by the same `serverError(STATIC_MESSAGE)` return with a static user-facing string.

The carryover from session 94 had already promoted the helper to `src/lib/api-logger.ts` (along with the test file) and migrated 7 of the model routes. This session finished the remaining 18 routes, bringing the total to 27.

**Why this lives in `api-logger.ts`** (not `api-response.ts`): the helper is a *catch-block shim* that composes two existing primitives (logApiError + serverError). The natural home is the file where the `logApiError` side-effect lives. `api-response.ts` is response-shape only (no logging), and adding a logging import there would break its "keep this module tiny and dependency-free" rule (see the `api-response.ts` top comment).

**Why not `setErrorFromCaught` / `toastError`-shaped** (which take a setter fn, not a log route): the API catch-block is a *combined log + response* contract — the setter-fn pattern is for client-side `useState` / `showToast` cases where there's no log side-effect. A dedicated `serverErrorFromCatch` matches the API contract (1 call → 1 log + 1 response) without forcing the caller to compose two helpers at every site.

**Byte-equivalence audit:** the helper returns the same `NextResponse` as `serverError(message)` and emits the same `console.error` line as `logApiError(route, context, error)`. Tests cover the log+response pair end-to-end via console-error spying + NextResponse inspection (the 6 byte-equivalence tests in `tests/unit/server-error-from-catch.test.ts` assert the helper equals the inline 2-line block for 5 input shapes: Error, empty Error, string, null, TypeError).

### Patterns to take forward

1. **"serverErrorFromCatch is the catch-block shim of setErrorFromCaught" pattern** — two parallel helpers, one for server-side catch blocks (log + return), one for client-side catch blocks (setter). Different return shapes (NextResponse vs void), different consumers. The audit recipe is a 1-line grep: `grep -nE "logApiError\([^)]*\);\\s*$" src/app/api/` followed by checking for the paired `return serverError(` on the next line. After this session: **0 hits in List 4 territory** (excluding the 2 dynamic-message sites + the 3 cleanup-line sites that intentionally don't fit the pattern).
2. **"Static vs dynamic message" discriminator for the migration** — the helper is only for the static-message variant. Sites that use `serverError(toError(error).message)` or `serverError(dynamicVar)` (3 sites in List 4) keep the inline form. The discriminator is: does the second argument to `serverError` reference the caught `error` or a local variable? If yes, keep inline. If no (it's a hardcoded "Failed to X" string), migrate.
3. **"Catch-block shim lives in api-logger.ts, not api-response.ts" pattern** — the helper is a log + response composition, not a response shape. `api-response.ts` is response-shape only (no logging) and has a "keep this module tiny" rule. The composition helper belongs with the log side-effect, not the response side-effect.
4. **"Test mock update when adding new exported helpers" pattern** — `tests/unit/profiles-sync-api.test.ts:7` had a `jest.mock("@/lib/api-logger", () => ({ logApiError: jest.fn() }))` that broke when `serverErrorFromCatch` was added to the export. The fix is mechanical: add the new export to the mock. Audit recipe: `grep -rn "jest.mock.*api-logger" tests/` → all consumers of the new helper must be updated.

### Refactor 1 — `parseDispatchMode(dispatchMode, schedule?)` in `src/lib/dispatch-mode.ts`

The 4-line 4-boolean decomposition was duplicated verbatim across 2 server-side files:

**`src/app/api/missions/route.ts:286-288`** (dispatch path):
```ts
const isSaveMode = dispatchMode === "save";
const isQueueMode = dispatchMode === "queue";
const isCronMode = dispatchMode === "cron" && scheduleVal;
```

**`src/lib/mission-promote-handler.ts:79-82`** (promote path):
```ts
const isSaveMode = dispatchMode === "save";
const isQueueMode = dispatchMode === "queue";
const isCronMode = dispatchMode === "cron" && input.schedule;
const isNowMode = dispatchMode === "now";

if (!isSaveMode && !isQueueMode && !isNowMode && !isCronMode) {
  return { ok: false, status: 400, error: "Invalid dispatchMode for promote" };
}
```

Both files had the same 3 `=== "literal"` lines and the same `&& schedule` truthiness gate. Extracted to a single `parseDispatchMode(dispatchMode, schedule?)` helper that returns all 4 booleans plus a `valid` boolean. The `valid` boolean lets the promote path write `if (!valid) return error` instead of the verbose 4-term negative boolean test. The dispatch path doesn't need `valid` (it doesn't reject unknown modes — the route's outer switch already handles that), so the 5th return field is destructured only where it's used.

**Byte-equivalence audit:** the helper returns the same 4 booleans as the inline form for every (mode, schedule) input shape. The `valid` boolean is `true` exactly when one of the 4 flags is `true` — this matches the original `!isSaveMode && !isQueueMode && !isNowMode && !isCronMode` negative test. Verified by 13 unit tests including a byte-equivalence matrix that asserts the helper equals the inline form for 10 input shapes (all 4 modes, undefined, empty, case-mismatched, cron-without-schedule, cron-with-empty-schedule, cron-with-whitespace-schedule, and the full valid/invalid combination matrix).

**Why `isCronMode` is `mode === "cron" && !!schedule` (not `?.trim()`):** the original inline form was `dispatchMode === "cron" && input.schedule` — a truthiness check, not a trim check. Whitespace-only schedules like `"   "` were treated as `isCronMode: true` by the original code (because `"   "` is truthy), and the call site did the `input.schedule?.trim()` check separately. The helper preserves that byte-equivalent discipline — a future "reject whitespace-only schedules at the parse site" change lands in one place (the helper) but is explicitly NOT made in this refactor.

**Rejected:** lifting the helper to a generic `parseEnum<T>(value, validValues, predicates)` that would work for any 4-value union. The 4 modes are not a generic enum (they have semantic-specific predicates like `isCronMode && schedule`), and the type union is closed. The single-purpose helper is the simpler form; promote to a generic on a 2nd dispatch-mode consumer appearing elsewhere in the codebase.

### Refactor 2 — `scheduleForDispatch(dispatchMode, schedule)` in `src/lib/dispatch-mode.ts`

The 1-line ternary `schedule: newDispatch === "cron" ? newSchedule : undefined` was repeated 3 times in `useMissionsPage.ts` (the 3 `dispatchPayload` overrides that merge a `schedule` field — one each in the update, promote, and dispatch branches of `handleCreate`). Extracted to a `scheduleForDispatch(mode, schedule?)` helper that returns the schedule verbatim for cron and `undefined` for the other 3 modes.

**Byte-equivalence audit:** the helper returns exactly `mode === "cron" ? schedule : undefined` for every input shape. Verified by 7 unit tests including a byte-equivalence matrix that asserts the helper equals the inline form for 7 (mode, schedule) combinations. The most subtle case: `scheduleForDispatch("cron", "")` returns `""` (not `undefined`) — this matches the inline form's verbatim return. The empty-string suppression (if any) is the caller's responsibility (e.g. the existing `input.schedule?.trim()` check in the API layer).

**Why this is a separate helper from `parseDispatchMode`:** `parseDispatchMode` is server-side (returns 4 booleans + valid), `scheduleForDispatch` is client-side (returns a single field for an API payload). Different consumers, different return shapes. Combining them would force every consumer to destructure both shapes.

### Refactor 3 — `joinCrontabLines(lines)` helper in `src/app/api/cron/hardware/route.ts`

The verbatim `lines.filter((l) => l.trim() || l === "").join("\n")` pattern was repeated 3 times in the hardware cron route (POST create line 334, PUT update line 423, PUT delete line 481). Extracted to an inline `joinCrontabLines(lines)` helper in the same route file (no new module — it's a 1-liner, not worth a separate file).

**Why inline, not `@/lib/`:** the helper is 1 line of pure function. Promoting to `@/lib/` would add a file boundary (and an import) for a function that's only used in this 1 route. The 3 call sites in the same file benefit from being a few lines apart from the helper definition. Promote to `@/lib/` on a 2nd route consumer (e.g. a future `software-cron/route.ts` that uses the same filter discipline).

**Byte-equivalence audit:** the helper returns exactly the same string as the inline form for every input. Verified by 6 unit tests in `tests/unit/join-crontab-lines.test.ts` including a byte-equivalence matrix that asserts the helper equals the inline form for 6 input shapes (empty, all-blank, mixed blanks, comment + entry blocks, whitespace-only middle lines, and the read-then-write round-trip case).

**The load-bearing bit:** the filter `(l) => l.trim() || l === ""` preserves intentionally empty lines (used as separators between job blocks in the on-disk crontab) while dropping lines that are only whitespace. A future "fix" that swapped to `.filter(Boolean)` or `.filter((l) => l)` would silently strip blank lines from the on-disk crontab, potentially concatenating job blocks. The helper + the byte-equivalence matrix lock this behaviour in.
