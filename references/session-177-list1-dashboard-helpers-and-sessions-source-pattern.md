# Session 177 — List 1 (Dashboard, Sessions, Memory, Logs) — `withCronJobSchedule` 4th-arg promotion + `scheduleDisplayFromParsed` adoption + Sessions source-pattern tests + Logs `lineCount` NaN guard

## What shipped

Four small, byte-equivalent cleanups on the List 1 surface:

1. **`withCronJobSchedule` 4th-arg promoted from `?` to required.** The `scheduleDisplay` parameter is now `string | null` (no longer `string | null | undefined`). The pre-session-177 `scheduleDisplay?: string | null` shape was a vestigial 2-shape handle — the helper either wrote `schedule_display: scheduleDisplay` (when supplied) or preserved the old value via a `...(scheduleDisplay !== undefined ? { schedule_display: scheduleDisplay } : {})` spread (when omitted). Today every call site already passes 4 args (the dashboard's `handleCronScheduleChange` derives `scheduleDisplay` from `parseSchedule(newSchedule).display` with a raw-input fallback for the `invalid` variant), so the optional-arg branch was dead code. Promoted to required + dropped the spread-conditional body — the helper now writes `schedule_display: scheduleDisplay` unconditionally (using a literal `null` when the caller passes `null`). The single caller in `src/app/page.tsx` was already passing 4 args, so the migration is 0 sites in production but trims 5 lines from the helper body. The new JSDoc explicitly documents the "writes a literal `null` for the no-label case" behaviour so a future caller knows what to pass.

2. **`scheduleDisplayFromParsed` adoption in the dashboard's `handleCronScheduleChange`.** The 4-line inline form `parsed.kind !== "invalid" ? parsed.display : newSchedule` was the only consumer of the `parsed.display` field on the discriminated `ParsedSchedule` union. The helper `scheduleDisplayFromParsed(parsed, fallback)` (in `src/lib/schedule/parse-schedule.ts`, added 2026-06-09 for cron-validator reuse) does the type-narrowing in a single audited place — the call site collapses to `const scheduleDisplay = scheduleDisplayFromParsed(parsed, newSchedule)`. Byte-equivalent: the inline form returned `parsed.display` for the 3 success variants and `newSchedule` for `invalid`; the helper does the same. The pre-177 code's `parsed.kind !== "invalid"` check was correct (the `display` field is present on all 3 success variants per the `parseSchedule` source) but leaked the type-narrowing concern to every consumer.

3. **New source-pattern test: `tests/unit/safe-api-call-data-source-pattern-list1-sessions.test.ts`.** The two Sessions pages (`src/app/(main)/sessions/page.tsx` + `src/app/(main)/sessions/[id]/page.tsx`) had no source-pattern pin for the `safeApiCallData` adoption, even though the Logs page (`safe-api-call-data-source-pattern-list1-logs.test.ts`) and the HindsightBrowser (`safe-api-call-data-source-pattern-list1.test.ts`) both did. The new file pins: (a) both pages import `useApiData` from `@/hooks/useApiData` (the `safeApiCallData`-backed hook), (b) neither contains the legacy `safeApiCall<{ data?: T }>` call shape, (c) neither contains `?.data?.X` double-indirection reads (the signature of the pre-migration bug), (d) both read the unwrapped shape directly (`data.sessions` / `data.messages`). 12 assertions / 2 describes — one per page, mirroring the Logs-page pin.

4. **NaN guard on the Logs `lineCount` setter.** The `<select>` onChange was `onChange={(e) => setLineCount(parseInt(e.target.value, 10))}` — a raw `parseInt` with no NaN guard. Today the 4 `<option>` values are 100/200/500/1000 (all valid), so the guard is currently dead. The future-proofing value is real: if anyone converts the `<select>` to a `<input type="number">` (a common ergonomic upgrade), `parseInt("")` returns NaN, which would propagate to the `useApiData` URL builder (`/api/logs?name=…&lines=NaN`) and break the request. The new body mirrors the API route's existing pattern (`parseInt(searchParams.get("lines") || "200", 10) + Number.isFinite + Math.min(..., 1000) + 200` default) so the page and the API enforce the same shape. Byte-equivalent for the current `<select>` (all 4 options pass `Number.isFinite && >= 1 && <= 1000`). The fallback (200) matches the API's default.

5. **New unit test: `tests/unit/dashboard-helpers-unit.test.ts`.** Closes a coverage gap — the two helpers in `src/lib/dashboard-helpers.ts` (`composeTemplateUrl` + `withCronJobSchedule`) were exercised only by the source-pattern test in `dashboard-list1-active-missions-and-setdata.test.ts` (which pins the call shape, not the helper's behavior). 7 new tests cover: `composeTemplateUrl` URL construction + literal-id contract, `withCronJobSchedule` null pass-through + both-fields-update + literal-null-write + input-immutability + no-match pass-through. The "does not mutate the input monitor" assertion is the most important one — the helper is called inside a React state-setter callback and any input mutation would break reference-equality checks downstream.

## Why these are byte-equivalent

- **`withCronJobSchedule`**: the helper's output for any (monitor, jobId, newSchedule, scheduleDisplay) input is identical pre and post refactor. The pre-refactor `...(scheduleDisplay !== undefined ? { schedule_display: scheduleDisplay } : {})` spread wrote `schedule_display: scheduleDisplay` for `string` inputs, and the post-refactor unconditional `schedule_display: scheduleDisplay` writes the same value. The "omitted" branch (where `scheduleDisplay` was `undefined`) is unreachable in the production codebase — the single caller in `src/app/page.tsx` always passes 4 args. **No byte difference** for any reachable input.
- **`scheduleDisplayFromParsed`**: the helper body is `return "display" in parsed ? (parsed.display as string) : fallback` (line 135 of `src/lib/schedule/parse-schedule.ts`). For the 3 success variants (`interval` / `cron` / `once`), `"display" in parsed` is `true` and the helper returns `parsed.display`. For the `invalid` variant, the helper returns `fallback`. The pre-177 inline form was `parsed.kind !== "invalid" ? parsed.display : newSchedule` — `newSchedule` is the `fallback` argument. **Byte-equivalent** for every reachable input. The "kind" → "in" switch is safe because the `invalid` variant is the only one missing the `display` field (the 3 success variants all have it set to a non-empty string per `parseSchedule`'s source).
- **Logs `lineCount` guard**: for `<option value={100|200|500|1000}>`, `parseInt("100", 10) === 100`, `Number.isFinite(100) && 100 >= 1 && 100 <= 1000` is `true`, `Math.min(100, 1000) === 100`. The 4 reachable inputs pass through byte-for-byte. The fallback `200` only fires for `parseInt` returning `NaN` (empty string, non-numeric input) — none of the 4 current `<option>` values can produce that.
- **Sessions source-pattern test**: this is a new pin, not a code change. The post-refactor shape (the "adoption" of `useApiData` for envelope-typed reads) is byte-equivalent to the pre-refactor shape (the file already used `useApiData`); the test just locks the post-state.
- **`dashboard-helpers-unit.test.ts`**: new test file, no production code changes. The helpers' observable behavior was already correct (the dashboard relies on it); the test just adds direct unit coverage.

## Patterns to take forward

1. **The "promote optional arg to required" cleanup pattern.** When a helper has an optional parameter with a single call site that always passes a value, the optional branch is dead code. Promoting to required + using the value unconditionally (with a `null` literal for the "no value" case, if needed) shrinks the helper body by 3-5 lines, eliminates the dead-branch concern, and forces every future caller to consciously decide what to pass. The same pattern is now applicable to other CH helpers — e.g. `composeTemplateUrl(templateId)` could be reviewed for similar 1-caller dead-branch patterns. Defer to a future session that explicitly opts in to the "optional-arg audit" recipe.

2. **"Type-narrowing helpers for discriminated unions" pattern.** The `scheduleDisplayFromParsed(parsed, fallback)` shape is a generic pattern for any discriminated union with a field that's present on N-1 of the N variants. The helper composes `"key" in parsed ? (parsed as { key: T }).key : fallback` so the consumer sees a single `(parsed, fallback) => T` call site. This pattern is also applicable to:
   - The `lookupMissionIdForCronSession(sessionId)` flow in `src/lib/session-repository.ts` — the result is a discriminated union on `source` (`mission` / `cron` / `api` / `cli`), and a future helper `displayLabelFromSessionRecord(record, fallback)` could centralize the title-derivation logic that's currently inlined at 4+ call sites.
   - The `CronJobRecord` → `CronJobBrief` projection in `src/app/api/monitor/route.ts:25-48` — a helper `toCronJobBrief(job): CronJobBrief` already exists, but a sibling `toSessionBrief(session): SessionBrief` (line 51-59) doesn't follow the same naming convention. Future cleanup: rename `toSessionBrief` → `toSessionBrief` + extract both into `src/lib/cron-and-session-briefs.ts` for testability.

3. **"Page mirrors the API's input-validation pattern" rule.** The Logs `lineCount` setter's NaN guard mirrors the API route's existing `parseInt + Number.isFinite + Math.min + 200` default. This is a generalizable pattern: **any client-side input that's also server-validated should mirror the server's validation shape** so a future change to the input (e.g. `<select>` → `<input type="number">`) doesn't introduce a client-server skew. The 4 existing `<option>` values all pass the new guard, so the migration is byte-equivalent for the current `<select>`, but the guard is a no-cost future-proofing. The same audit could be applied to:
   - The Missions page's category filter (currently an enum-typed `<select>`)
   - The Dashboard's "syncNow" trigger (no user input, but the API could change)
   - Any future numeric input on a CH page

4. **"Source-pattern test for the safeApiCallData adoption is a class-level recipe."** The 3 List 1 source-pattern tests for `safeApiCallData` (Logs, HindsightBrowser, Sessions) form a complete coverage matrix for the envelope-typed read path. The sister List 2/3 tests (`safe-api-call-data-source-pattern-list2.test.ts`) cover the rest of the codebase. A future session could:
   - Extend the source-pattern tests to other API consumer surfaces (admin, fs, agent, etc.) — these are currently unpinned.
   - Add a "wraps every route response in `{ data: T }`" source-pattern test on the API side (asserting every route handler uses `ok(...)` / `created(...)` / `badRequest(...)` / etc. — no inline `NextResponse.json({...}, {status:...})` shapes).

5. **"List 1 is mined clean at the catch-block, envelope-unwrap, and dashboard-helper scopes" milestone.** The session 176 closure + this session's tests mean the surface has no outstanding 2-hop catch blocks, no legacy `safeApiCall<{ data?: T }>` sites, and direct unit coverage for the dashboard helpers. Future List 1 refactors would need to pick a new scope (e.g. UI-handler shape, state-derivation memo, type-narrowing audit) — the existing 5 sessions (118, 121, 144, 171, 174, 175, 176, 177) have closed the obvious gaps.
