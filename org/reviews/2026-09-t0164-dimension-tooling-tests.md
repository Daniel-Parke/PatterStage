## SQLite column inventory and recovery limit

The fresh fixture used the real `getDb()` migration chain, not regexes over `CREATE TABLE`. It set `PS_DATA_DIR` to a new OS temporary directory **before** importing the DB module, queried `sqlite_master` and `PRAGMA table_info`, closed the connection and removed only that fixture. The local sandbox's `tsx` loader first failed in `os.userInfo()`; a process-local stub allowed `tsx/cjs` to load. No app server, operator database or production migrator was launched. The resulting inventory had 49 application tables and 529 columns at `schema_version=43`; sorted `table.column` entries joined with LF and a final LF hash to SHA-256 `c892bfb802303e2b5aa49096daa1e55449a9c0734cd16534b1497bbe159a93d3`. `benchmark_runs` has 23 columns, `sessions` 15, `sync_registry` 6. There are 42 shipped SQL migration files (001–043, with 010 absent). Focused real-SQLite `npx jest --runInBand --runTestsByPath tests/unit/run-migrations-upgrade.integration.test.ts tests/unit/db-baseline.test.ts --silent` passed 8/8.
